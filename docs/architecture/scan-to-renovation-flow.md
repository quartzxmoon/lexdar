One LiDAR scan (`ScanProject`) can carry many independent renovation ideas
(`RenovationPlan`) — "Open concept kitchen", "Guest bath — option A" — each
tracking its own wall removals, material swaps, and placed furniture/fixture
items without touching the original scan data.

## Flow

1. **Capture** — `RoomCaptureCoordinator` wraps Apple's `RoomCaptureSession`
   / `RoomCaptureView` (RoomPlan). `ScanCaptureView` drives
   start → scan → finish → name → save.
2. **Persist** — `ScanStore.saveNewScan` exports the processed `CapturedRoom`
   two ways into `Documents/Scans/<scanID>/`: a `.usdz` (via
   `CapturedRoom.export(to:exportOptions: .parametric)`) for AR Quick Look,
   and the raw `CapturedRoom` as a JSON file named room.json (it's natively
   `Codable`) so it can be reloaded without re-scanning.
3. **Plan** — `ScanDetailView` creates a `RenovationPlan` per idea. A plan
   is just: `removedWallIDs: Set<UUID>`, `surfaceMaterials:
   [SurfaceMaterialOverride]`, `placedItems: [PlacedItem]`, keyed by
   RoomPlan's own `CapturedRoom.Surface.identifier` — **not** by array
   index, because array order is not guaranteed stable across re-processing.
4. **Edit** — `RenovationEditorView` + `RenovationSceneView` render the
   scan + plan together via `RoomSceneBuilder.build(room:plan:)`, which
   rebuilds the whole `SCNScene` from scratch on every plan mutation
   (walls flagged removed are simply skipped when building the scene, not
   hidden after the fact).
5. **Export** — `RenovationSummaryView` renders a PDF directly with
   `UIGraphicsPDFRenderer` (no layout engine) summarizing wall removals,
   material changes, and the itemized furnish/fixture list.

## Catalog

`Catalog.swift` is static Swift data, not a database — `CatalogItem.id` is
a stable string (e.g. `"kitchen.sink.farmhouse"`) stored on `PlacedItem` and
`SurfaceMaterialOverride`, resolved back to a `CatalogItem` via
`Catalog.item(id:)` at render/export time. Items render as dimensioned
primitive shapes (box/cylinder/plane) by default; `CatalogItem.assetName`
is reserved for swapping in real `.usdz` models later (see README).

> ⚠️ `RenovationPlan.removedWallIDs` / `surfaceMaterials` are keyed by
> `CapturedRoom.Surface.identifier`, which Apple's docs describe as stable
> for the life of one `CapturedRoom` — re-running RoomPlan capture on the
> same physical room produces a **new** `CapturedRoom` with new
> identifiers. A `RenovationPlan` is therefore only valid against the exact
> `CapturedRoom` (the exact `scanID`) it was created for; it cannot be
> replayed onto a re-scan of the same space.

> ⚠️ `RoomSceneBuilder.placedItemNode` composes two rotations for `.plane`
> primitives (a -90° tip to lie flat, then the item's `rotationY`) using
> `simd_quatf` multiplication in a specific order (`yaw * layFlat`).
> Reordering that product changes which axis the yaw rotates around after
> the tip and silently breaks rug/outdoor-footprint placement.

> ⚠️ `project.pbxproj` is hand-generated by a one-off script (not committed;
> see git history around commit `fa5001d`), not authored in Xcode. Every
> `PBXFileReference.path` must be just the file's **basename** — each
> containing `PBXGroup` already supplies its own subdirectory via its own
> `path` (e.g. the Models group's `path = Models;`), and Xcode concatenates
> group path + file path. Using a file's full repo-relative path as the
> fileref path (e.g. `"Models/ScanProject.swift"`) doubles the subdirectory
> (`Models/Models/ScanProject.swift`) and fails with "Build input files
> cannot be found" — this broke the very first CI run. If the project ever
> needs more files added by hand-editing the `.pbxproj` rather than through
> Xcode, check this rule again.
>
> Also: the generator assigns a fresh random target id on every run, so
> `Lexdar.xcodeproj/xcshareddata/xcschemes/Lexdar.xcscheme`'s
> `BlueprintIdentifier` references go stale each regeneration and must be
> `sed`'d to the new id (printed by the generator script) — missed once
> already, caught before commit both times since the scheme simply
> wouldn't resolve. Do this every time the generator is re-run — including
> for [[blueprint-production]]'s files, which live in this same project
> and go through the same generator script. The `frameworks` list in the
> generator (RoomPlan/ARKit/SceneKit/QuickLook/PDFKit, now also
> PencilKit/PhotosUI for [[blueprint-production]]'s markup/photo features)
> needs a new entry whenever a new system framework is imported, same as
> a new source file needs an entry in `swift_files`.

> ⚠️ `RoomCaptureViewDelegate` inherits from `NSCoding` (confirmed on
> Apple's own doc page for the protocol — easy to miss since it's an
> unusual thing for a delegate protocol to require). Any type conforming
> to it, including `RoomCaptureCoordinator`, must also implement
> `init?(coder:)` and `encode(with:)`, even though the coordinator is
> never actually archived/unarchived. This was the real compile failure
> behind the first *honestly-reported* CI failure (after the pipefail fix
> below stopped masking it).
>
> Mark both `init?(coder:)` and `encode(with:)` **`nonisolated`**: the
> class is `@MainActor`, so without it both methods are implicitly
> MainActor-isolated, but `NSCoding`'s requirements are nonisolated —
> Swift 6 language mode treats the mismatch as an error (a warning under
> this project's current settings, caught in CI anyway). Neither method
> touches actor-isolated state, so `nonisolated` is free here.

## Entry point: Design & Renovate

`ScanDetailView` leads with a "Design & Renovate" button (`startDesigning`). It opens
the scan's most recent `RenovationPlan`, or creates one named "My Design" first, so
furnishing and finishing is one tap from the scan instead of buried under
"New Renovation Plan". Not yet run on a device.

## Renovation editor: placing items and drawing walls

- **Place Item** opens the furnish catalog; choosing an item sets
  `pendingPlacementItemID`, and `RenovationSceneView.updateUIView` hands it to
  the coordinator, which drops the item on the floor under the middle of the
  screen (resting on the floor, or hung from the ceiling for pendants), selects
  it, and returns to Select so it can be dragged straight away. Dragging uses a
  ray-to-floor-plane intersection (`floorPoint(at:planeY:)`) so the item follows
  the finger.
- **Draw Wall** (`RenovationTool.drawWall`) switches to a top-down camera and
  turns a one-finger/Pencil drag into an `AddedWall` stored in
  `RenovationPlan.addedWalls`, snapped to existing wall ends, 15 degree angles
  and a 5 cm grid. New walls render as `newwall:<uuid>` nodes; Remove Walls on
  one deletes it, and Wall Finish can paint it.

> ⚠️ The old placement flow waited for a tap on a `floor:` node. If RoomPlan
> returns no floor surfaces, nothing could be hit and the tap silently did
> nothing. `RoomSceneBuilder` now adds a synthetic floor slab (fixed id
> `syntheticFloorID`) when `room.floors` is empty, and placement/drawing
> intersect an imaginary plane at the scan's floor height (from the walls)
> instead of depending on a floor node.

> ⚠️ `RenovationPlan.addedWalls` is optional so plans saved earlier still decode;
> read it through `newWalls`. New walls are not in the 2D plan view, the
> renovation summary export, or any export format yet. Compile-checked in CI
> only; never run on a device, so gesture feel (snapping distances, drag
> response, top-down framing) is untested.

## Furniture and fixtures switch

RoomPlan always detects furniture and fixtures (`CapturedRoom.objects`), and
its own scanning view always draws them, so the switch works on what the app
saves and shows. `ScanCaptureView` has a "Furniture & fixtures" toggle
(remembered in `@AppStorage("scanIncludeObjects")`) that also hides them in the
live preview; the choice is stored as `ScanProject.includeObjects` and can be
flipped later in `ScanDetailView` ("Scan Options"). Off hides them in the
fixtures list and the renovation editor (`RoomSceneBuilder.build(...,
showDetectedObjects:)`) and rebuilds the USDZ without them.

> ⚠️ `room.json` always keeps the full scan; only display and the exported
> USDZ change, so the switch is reversible. The USDZ has no objects because
> `ScanStore.withoutObjects` edits the room's JSON form (key `"objects"`) and
> decodes it again, since `CapturedRoom` has no public initializer. That key
> name is an assumption about RoomPlan's coding format; if it is wrong the
> function returns nil and the model keeps its objects while everything else
> still honors the switch. Not yet checked on a device.

> ⚠️ `ScanProject.includeObjects` is optional (nil means included) so scans
> saved before the switch still decode. RoomPlan's own camera overlay during
> scanning still outlines furniture whatever the switch says.

## Live 3D preview while scanning

While a scan runs, `RoomCaptureCoordinator` receives RoomPlan's
`captureSession(_:didUpdate:)` callbacks (a fresh in-progress `CapturedRoom`),
keeps at most one every 0.6 s in `liveRoom`, and `ScanCaptureView` shows
`LiveRoomPreview` in the top corner: a slowly spinning dollhouse built with
the same `RoomSceneBuilder` as the editor, so walls, doors, windows, and
objects appear in 3D as they are found. It hides itself when scanning stops
(RoomPlan's own view then shows its processed result).

> ⚠️ Every update rebuilds the whole preview scene from scratch (as
> `RoomSceneBuilder` always does), which is why updates are throttled. If the
> preview stutters on a large scan, lengthen the throttle in
> `RoomCaptureCoordinator.acceptLiveUpdate` before touching anything else.
> Not yet run on a device; the camera framing in `LiveRoomPreview` (distance
> from the room's bounding box) is a guess to tune once seen.

## Look, library, and levels

- `MaterialTextures` draws wood, tile, brick, siding, shingle, carpet and similar
  textures once per catalog item (cached) and `RoomSceneBuilder.surfaceMaterial` tiles
  them at real-world scale on floors, walls, and exteriors.
- `ItemModels` builds multi-part shapes (sofas, beds, trees, stairs, roofs, pools,
  garages, glass showers, free-standing tubs, doors, windows) from the item's id.
  Items it does not recognize fall back to the plain box in `RoomSceneBuilder`.
- `CatalogExtra` holds the larger library: more flooring and wall finishes, exterior
  finishes, roofs, stairs, doors and windows, foundations and structures,
  landscaping, decor, storage, and more kitchen, bath, appliance, furniture, lighting
  and outdoor items.
- The editor's level menu (`RenovationEditorView.level`, `RenovationSceneView.levelIndex`)
  moves where new walls and items are placed up or down by one story height.

> ⚠️ Keywords in a catalog item's id decide its model (`ItemModels.kind(for:)`) and
> texture (`MaterialTextures.pattern(for:)`). Order matters: earlier checks win, and ids
> share words ("furn.deskchair" must be caught as a chair before "desk" makes it a table).
> A new item with an unlucky id silently falls back to a box or flat color.

> ⚠️ Each model is built centered on the item's dimension box, with `y` measured up from
> its bottom, because placement assumes the node's origin is the middle of that box.
> Parts must not be named: tap handling resolves the nearest *named* ancestor
> (`RenovationSceneView.Coordinator.tag`) so any part selects the whole item.

> ⚠️ Levels only move placement height. Upper stories get no automatic floor slab or
> stair opening; place an "Upper Floor Deck" from Structures. Roofs, yard items, and
> structures may be placed outside the scanned room's bounds; everything else is clamped
> inside it at placement. Compile-checked in CI only; the look of the models and
> textures has never been seen on a device.

## Multi-room scanning

Open-plan spaces collapse to the first closed room in RoomPlan's processed result.
`RoomCaptureCoordinator.finishRoom` stops with `stop(pauseARSession: false)`, so the AR
session stays continuous; `scanNextRoom` re-runs the same session. Each processed room is
appended to `completedRooms` (once, guarded by `awaitingRoom`) and `mergedRoom` combines
them with `StructureBuilder`, falling back to `merge` (plain concatenation through the
rooms' JSON form).

> ⚠️ `merge` assumes RoomPlan encodes `walls`, `doors`, `windows`, `openings`, `objects`
> and `floors` as top-level arrays, the same unverified assumption as
> `ScanStore.withoutObjects`. `StructureBuilder`'s `rooms` property and async signature
> are also unchecked beyond CI compiling. If the app is backgrounded between rooms the AR
> session is no longer continuous and rooms will not line up (relocalization with an
> `ARWorldMap` is not implemented). Never run on a device.

## Not yet built

- No native `.usdz`/Reality asset loading path for catalog items — see
  `CatalogItem.assetName` and the README section "Swapping in real 3D
  assets".
- Multi-room scanning exists but has never run on a device (see below).
- Wall removal / material swap is a **visual planning aid only** — nothing
  in this codebase checks structural/load-bearing concerns.
